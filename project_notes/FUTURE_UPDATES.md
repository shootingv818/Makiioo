# موارد آینده ثبت‌شده در طرح

ترتیب آینده مصوب:

1. backup، ثبت rollback commit و MD5 هسته
2. اصلاح lifecycle پورتال و Custom Domain
3. ساخت storage و event model پورتال
4. پیاده‌سازی `attempt_id` و cleanup پنج‌دقیقه‌ای
5. اتصال UI تأییدشده به API واقعی
6. آمار، پنل پورتال و کارت خلاصه `/start`
7. کارت‌های گزارش کامل
8. ناظر محدود برای وضعیت پورتال و حذف session نامعتبر قطعی
9. متن خودکار پس از ورود با sender موجود
10. ارسال چنداکانتی تلگرام با صف مشترک، failover، cooldown و checkpoint
11. تست failure، concurrency و restart؛ سپس syntax check و کنترل MD5 هسته
12. push روی شاخه جدید، PR به `production` و deployment امن پس از merge

ایده‌های قابلیت «مغز»، بازطراحی کلی ربات و قابلیت‌های خارج از طرح جزو این آپدیت نیستند.

# فرستنده مخفی (بدون برچسب فوروارد) — ثبتِ نتیجه‌ی واقعی

> ثبت: ۲۰۲۶-۱۱-۰۵ · بازنویسی: ۲۰۲۶-۱۱-۰۳ (پس از تست مالک)
> قاعده‌ی مالک: **کد فوروارد حذف نشود.** رعایت شد؛ `rb.forward_message`
> و همه‌ی صداکننده‌هایش سر جای خودشان هستند.

## مسئله

ارسال با `rb.forward_message()` از Saved Messages بالای پیام برچسب
«Forwarded from …» می‌زند، پس گیرنده می‌فهمد پیام دست‌به‌دست شده.

## راه ۱ — تنظیم حریم خصوصی `link_forward_message` → ❌ رد شد (تست واقعی)

ساخته شد (`rubika/forward_privacy.py` + دکمه در ⚙ ستینگ)، روی اکانت واقعی
اجرا شد، `setSetting` **موفق** برگشت و مقدار با `getPrivacySetting` هم
تأیید شد — ولی **برچسب فوروارد در پیامِ دریافت‌شده سر جایش بود.**

نتیجه: این تنظیم (مثل تلگرام) فقط **لینکِ** نام فرستنده را برمی‌دارد، نه
خودِ برچسب را. ماژول و دکمه‌اش **کامل حذف شدند**.

> درسِ گران: این فیچر روی یک فرضِ **تست‌نشده** ساخته شد و یک ساعت وقت گرفت.
> هیچ API روبیکا پارامتری برای «پنهان‌کردن نام ارسال‌کننده» ندارد —
> `rubpy` / `pyrubi` / `RubikaLib` هر سه فقط `from_object_guid`,
> `to_object_guid`, `message_ids`, `rnd` می‌فرستند. **قبل از ساختن، تست.**

## راه ۲ — ارسال کپی به‌جای فوروارد → ✅ پیاده شد

خودِ اپ روبیکا هم همین کار را می‌کند: فوروارد نمی‌کند، یک **پیام نو**
می‌سازد، پس هیچ هدر فورواردی ساخته نمی‌شود. `rubika/copy_send.py`:

1. پست مارک‌شده در Saved Messages **یک بار** خوانده می‌شود →
   `file_inline` + کپشن
2. برای هر مخاطب: `send_message(guid, text=caption, file_inline=<همان ارجاع>)`

فایل **دوباره آپلود نمی‌شود** (همان ارجاعِ سروری)، پس سرعت ارسال عوض نمی‌شود.

## فقط یک شیوه‌ی ارسال: «🫥 File + Caption, HIDDEN»

روشِ قبلیِ مبتنی بر مارکر (`sendhidden_`) **حذف شد**، چون وابسته بود به
این‌که مالک دستی یک پست با مارکر در Saved Messages آن اکانت گذاشته باشد — و
روی ورکر خراب می‌شد («No message with marker … in the worker's Saved
Messages»).

مسیر فعلی، کاملاً از منطقِ موجودِ خودِ پروژه ساخته شده:

1. فایلِ ذخیره‌شده‌ی مالک با **همان متد آپلودِ خودمان**
   (`caption_file.upload_for_account`) در Saved Messages همان اکانت آپلود
   می‌شود — با همان fallback ورکر/IP.
2. **ارسال روی همان نودی اجرا می‌شود که فایل واقعاً آن‌جا نشسته**
   (`out["worker"]`). اگر IP خانه بلاک بود و آپلود روی ورکر دیگری انجام شد،
   ارسال هم همان‌جا می‌رود.
3. pre-flight روی همان ورکر با `/prepare` موجود: هم تأیید می‌کند پست
   پیدا می‌شود، هم `hidden_supported` را می‌خواند.
4. ارسال با موتور موجود (`run_send` / `run_send_remote`) و فقط یک فلگِ
   افزودنی `hide_sender` در payload.

## گاردها (هیچ‌کدام «سکوت» نمی‌کنند)

* **ورکر قدیمی:** اگر `hidden_supported` نبود → `_OLD_WORKER` و کارتِ
  «Workers → Update All». **هیچ پیامی ارسال نمی‌شود.**
* **پست خوانده نشد:** هم موتور local و هم `/send/start` ورکر، اجرا را
  **رد می‌کنند** و نه این‌که به فوروارد برگردند. فوروارد در این حالت یعنی
  اسم مالک روی هر ۵۰۰ پیام.
* **آپلود شکست خورد:** ارسال هیچ‌وقت شروع نمی‌شود.

## باگ ۵۰۰ که همین‌جا رفع شد

`/send/start` خط ۶۳۶: نوشته شده بود `mode != "text"` در حالی که متغیرِ
in-scope `send_mode` بود → `NameError` → HTTP 500 روی ورکر.
`compileall` این کلاس باگ را نمی‌گیرد و pyflakes در سندباکس نصب نمی‌شود، پس
`_stubs/test_scope.py` با `symtable` نوشته شد و همه‌ی ۳۷ فایل را چک می‌کند.
همان تست، ۶ برانچِ مرده‌ی `await_tg_*` را هم پیدا کرد (باقی‌مانده‌ی حذف
تلگرام) که هر کدام یک `NameError` خفته بودند.

## چیزهایی که دست نخورده‌اند

`rb.forward_message` و همه‌ی صداکننده‌هایش، مسیر مارکر، متن دلخواه،
File+Caption معمولی، ساخت کانال، مغز، مغز کانال، مغز استخری، انتقال ورکر، و
فایل‌های pinned (`core/`, `rubika_client.py`, `worker.py`, `main.py`,
`config.py`, `portal/`, `features.py`, `login_code.py`) — با diff تأیید شد: صفر تغییر.

## تأییدِ باقی‌مانده

این‌که پیامِ **دریافت‌شده** واقعاً برچسب فوروارد ندارد، فقط با یک تست روی
شماره‌ی واقعی اثبات می‌شود. تا آن تست، «کار می‌کند» اعلام نمی‌شود.
